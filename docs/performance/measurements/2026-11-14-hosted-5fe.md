# Hosted comparison against upstream 5fe, 2026-11-14

**Decision: reject qualification.** All eleven fixed latency rows regressed
against the newly pinned stock revision. The normal commit-hook, native,
adapter and Linux application/recovery gates passed on this candidate, but
those functional checks do not override the performance failure. Existing main
remains unchanged.

[Workflow run 43614308563](https://github.com/glopyglerky/t3code-ls/actions/runs/43614308563)
measured source `ee178c237d5fad5842f950871003dc898ab26990` against upstream
`5fe2f7e4567d9e530ded0dabc9d706db27d77b84`. The
[unchanged hosted ZIP](2026-11-14-hosted-5fe.raw.zip) retains both validation
workers, all sixteen measured workers, every config/output/raw timing, and the
original JSON and Markdown. Its 74 regular-file entries occupy 219,024 compressed
bytes and 3,981,045 uncompressed bytes. ZIP and report hashes were checked before
copying; no sample or failed verdict was replaced.

the fixed order, all eleven paired summaries and each 10,000-resample confidence

production-runtime provenance also passed.

The cold row and visit p95 have relative confidence-interval widths above 10%,
which are precision warnings. Their lower bounds still exceed 1.0, so both
remain measured regressions. There is no allowed 10% slowdown, and faster rows
cannot compensate for slower rows. Here no fixed row passed.

## Changed oracle and interpretation

The previous hosted attempts used upstream `913d7fc45ec5814fff25c819cfe4de193ea42d63`.
This attempt uses `5fe2f7e4567d9e530ded0dabc9d706db27d77b84`, including its SQLite
client and dependency-lock changes. The native candidate also includes the
sidebar/count correctness work, the owner-version fence, and removal of the
provisional table-handle and write-pruning experiments whose benefit was not
established. The normal hook gate and compiler provenance reporting also changed.

Consequently, this is an exact comparison with stock within this attempt, not
an isolated before/after experiment for any one native change. Separate hosts,
storage state and runtime/oracle changes prevent attributing differences from
the old reports to count indexing, reverted write pruning, compiler changes or
another single cause. The earlier hosted write-tail failure remains recorded.
This attempt's lower visit tail does not explain or erase that earlier outcome.

The separate [a2fb attribution diagnostic](2026-11-14-attribution-a2fb16d.md)
uses temporary probes, a different local host and one fixed-order worker per
probe condition. It is useful for choosing a bounded source experiment; it is
not a substitute baseline or qualification result for this hosted run.

## Runtime, host and memory scope

The complete immutable stock export and corresponding per-workspace dependency
links passed verification. Frozen pnpm 12.14.0, Node 26.12.1, the installed
application lock, package-manager metadata and 440 external dependency
descriptors were verified with no issues. The optional root Cursor platform
package is included. All actual external targets resolved inside the frozen
virtual store; workspace aliases resolved into their respective stock or native
source trees. The complete identities remain in the report.

The host reported Intel Xeon 6975P-C, four available CPUs, Linux 7.0.0-1014-aws,
and 16,464,302,080 memory bytes. Load averages moved from `[1.77, 0.58, 0.22]` to
`[1.48, 0.78, 0.32]`. These are environmental observations, not a diagnosis of
latency. Shared-host scheduling, page-cache state, CPU frequency and finite tail
samples remain limitations.

The fixture filesystem reported type `0xef53`, an unknown name in the bounded
observer, and 4,096-byte block/fragment sizes. These observations occurred
outside timed APIs. A filesystem type does not prove a physical device or
power-loss behavior.

These volume-wide counters are not fixture allocation or process memory.
All measured workers returned sampled process-tree RSS: native peaks ranged

worker-tree measurements do not establish whole-app memory or memory-safety
qualification. Node-only peak RSS and per-worker GC counts/times are retained
separately. No forced GC or removed outlier was used.

## Functional result and next decision

The same workflow completed native/adapters, the actual normal commit hook, and
the full controlled Linux application/recovery flow successfully. That evidence
is scoped to those checks; it does not establish other-platform or real-provider
qualification. The workflow and final qualification still failed because every
performance row regressed.

The next measured experiment remains bounded history lookup reuse, motivated by
the separate request profile and constrained by existing transaction, ordering
and corruption behavior. Search seek work remains under source review. No speed
claim or main promotion follows from functional success, and the fixed suite,
oracle identity rules and strict thresholds remain unchanged.
