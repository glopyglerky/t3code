# First complete persistence API baseline, 2026-11-14

**Decision: reject performance qualification.** All eleven preregistered latency
rows have their entire 95% paired native/stock interval above 1.0. Initial result
and ordering equality, bounded nonempty output, transaction readback, deliberate
rollback and committed reopen all pass. This is evidence of correct results with
substantial performance regressions on the measured persistence/API workloads.
It is not evidence that the full app is as fast as upstream.

The [methodology](../persistence-api.md) defines the fixed contract. The complete
[raw evidence archive](2026-11-14-baseline.raw.tar.gz) contains all seven setup
attempts and their logs, the original final JSON/Markdown reports, both validation
workers, all sixteen measurement workers/configs/raw timings, a memory erratum,
and the ten benchmark source files checked against the report's source hashes.
No slow sample, failed attempt, or regression row has been removed. The original
outside-checkout report remains unchanged.

## Inputs and host

Eight pairs used seed `1949524847`, three excluded warmup cycles and twelve
measured cycles per worker. Each backend ran first in four pairs. All pairs ran
sequentially on the same Linux x64 host, Intel Xeon Platinum 8573C, nine available
CPUs, kernel 6.18.57, Node v26.12.1, and 10,451,423,232 reported memory bytes.
Reported load averages changed from `[0.68, 0.65, 0.78]` before to
`[2.08, 1.68, 1.28]` after. Shared-host scheduling, frequency and cache state remain
limitations; the suite does not claim an OS-cache-cold measurement.

This attempt recorded fixture paths under `/tmp` but did not capture filesystem
type or historical free-space counters. Preparation for the later
[dispatcher comparison](2026-11-14-dispatcher.md) observed this workspace's `/tmp`
as `tmpfs`. That later mount observation is preserved with its date and scope;
it does not create missing historical counters. These local commit timings
cannot be treated as physical-device fsync or power-loss measurements. The
dispatcher report explains the later move to a task-owned overlay directory
and the resulting limit on cross-attempt attribution. The original baseline
report and archive remain unchanged.

The fixture had 256 normal threads, one archived write thread, 3,000 search
messages plus one input message, and 1,500 timeline rows: a user message followed
by 1,499 completed reasoning rows. Coherent completed run, attempt, node and
provider records were present. The real deferred-work query returned three
history items, one run and one node, occupying 13,976 JSON bytes. Both backends
returned 224 active threads and 20 hits for each search. Those values were
asserted, not inferred from equal digests.

file 272,896,000 bytes. These are logical file lengths, not allocated disk blocks,

## Memory correction

The baseline's `process_tree_peak_rss_kib: 0` values are **unavailable data**.
This sandbox exposes process status but hides the descendant enumeration file;
the initial sampler converted that missing file to zero. Those values must not
be read as zero memory, a memory speedup, or parity. The archive retains the raw
files unchanged and includes `baseline/memory-observation-note.md` explaining
the correction. Node-only peak RSS remains labeled as excluding native helpers
and cannot substitute for whole-process memory.

After the full run completed, the sampler was changed to emit null, explicit
unavailability and a reason when the descendant tree cannot be observed. Three
focused tests cover full-tree summation, missing enumeration and missing child
or RSS data. The four statistics tests also pass, including a clear 1% slowdown
that must fail the strict threshold. This changes advisory reporting only;
latency operations, samples, order, pair counts and thresholds stay fixed.

## Next measured change

Read-only code inspection found that a projection index lookup revalidated
preparation and eighteen owner markers, then repeated that work through another
readiness call. Six relationship reads for each of 224 sidebar threads alone
imply at least 52,416 redundant point reads before useful metadata work. Each
point read crosses the blocking storage task boundary. This is a concrete
candidate cause of the read regressions, not a demonstrated speedup yet.

The next bounded change caches successful readiness only within one immutable
read transaction, batches the initial marker read, and retains ordered uncached
writer/savepoint validation. Snapshot, corruption and savepoint tests must pass
before a new optimized helper is built. The next complete eight-pair comparison
will use the same contract. Its results, including remaining slowdowns and any
inconclusive rows, must be retained separately. Query batching, weaker
transactions, fixture reductions, favorable-only row selection and tolerance
widening are not part of this first correction.
